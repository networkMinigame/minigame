# 네트워크 미니게임 파티 - 아키텍처 기준안

> 이 문서는 확정안이 아니라 **기준안**이다. 팀원이 보면서 고치고 같이 맞춘다.

## 0. 게임 개요 (지금까지 정한 것)

- 폼멜파티 느낌의 **실시간 미니게임 연속** 게임. 보드판/턴제는 없음.
- 인원: 2인 기준으로 개발, **3~4인은 접속만 늘리면 되게** (코드에 "2명"을 박지 않음).
- 서버 PC 한 대 + 터널링(Tailscale 등)으로 접속.
- 라운드마다 HP, 아이템, 왕관(승점)이 이어지고, **정해진 라운드 수**가 끝나면 왕관이 가장 많은 사람이 승리.

### 라운드 흐름

1. **아이템 단계 (10~15초)**: 모두 동시에 아이템과 대상을 고르고, 타이머 끝나면 한꺼번에 발동
2. **미니게임 소개 (3초)**: 규칙 한 줄 + 카운트다운
3. **미니게임 (30~60초)**: 빠른 개인전
4. **결과 (5초)**: 등수에 따라 왕관, 아이템, HP 변화

## 1. 붙여넣은 초안 검토 결과

### 사실 확인

| 내용 | 판정 | 비고 |
|---|---|---|
| JDK 25는 LTS | 맞음 | 2025-09-16 릴리스 |
| 가상 스레드 synchronized 핀닝 해결 | 맞음 | JEP 491, JDK 24에서 들어옴 |
| 구조적 동시성(Structured Concurrency) 표준화 | **틀림** | JDK 25에서도 5번째 프리뷰(JEP 505). `--enable-preview` 필요. **사용 안 함** |

참고: [JEP 491](https://openjdk.org/jeps/491), [JEP 505](https://openjdk.org/jeps/505), [JDK 25 JEP 목록](https://openjdk.org/projects/jdk/25/jeps-since-jdk-21)

### 유지할 것

- **`\n`으로 끝나는 한 줄 = 메시지 하나** (줄 단위 메시지)
- **소켓마다 송신 큐 + 송신 스레드**: 여러 스레드가 한 소켓에 동시에 쓰면 메시지가 섞임. 느린 클라이언트 한 명 때문에 broadcast 전체가 막히는 것도 방지
- **클라이언트 수신 → `SwingUtilities.invokeLater`로 EDT에 넘기기**
- FlatLaf, record로 메시지 정의

### 바꿀 것 (중요한 순서)

1. **게임 루프 스레드 하나가 게임 상태를 전부 맡는다** (가장 중요)
   - 초안: 클라이언트별 스레드가 디스패처를 거쳐 게임 로직을 직접 실행 → 4개 스레드가 HP/위치를 동시에 건드려 락 문제 발생
   - 변경: **수신 스레드는 파싱해서 공용 입력 큐에 넣기만**, **게임 루프 스레드 1개**가 20~30Hz로 큐 비우기 → 상태 갱신 → broadcast
   - 게임 상태를 한 스레드만 만지므로 synchronized가 거의 필요 없음 (핀닝 고민도 사실상 무관)
2. **`ConcurrentLinkedQueue` → `LinkedBlockingQueue`**
   - `ConcurrentLinkedQueue`는 비었을 때 기다리는 기능이 없어 송신 스레드가 바쁜 대기로 CPU를 잡아먹음
   - `LinkedBlockingQueue.take()`는 메시지가 올 때까지 잠듦
3. **핸들러에 `Socket`을 직접 넘기지 않는다**
   - `handle(GameRequest, Socket)`이면 송신 큐를 우회해서 직접 쓸 수 있음
   - `Session`(playerId + 송신 큐)을 넘기고, 보낼 때는 무조건 `session.send(...)`
4. **리플렉션 서블릿(@GameServlet) 대신 sealed interface + record + switch**
   - 표준 자바에는 어노테이션 붙은 클래스 자동 스캔 기능이 없음 (라이브러리 또는 수동 등록 필요)
   - 메시지 종류가 20개 미만이라 과함. sealed + switch는 빠진 case를 컴파일러가 잡아줌
5. **`payload`를 String으로 두지 않는다**
   - JSON 안에 JSON 문자열 → 파싱 두 번. 타입별 record로 바로 받기
6. 자잘한 것
   - **JSON 라이브러리 필요** (Gson/Jackson). 싫으면 수업 예제처럼 `MOVE|1|0` 문자열 프로토콜도 충분
   - **DB(JDBC) 제외**: 한 판 끝나면 끝나는 게임. 전적 저장은 여유 되면
   - **가상 스레드**: 써도 되지만 4인 게임에선 일반 스레드와 차이 없음. 팀이 익숙한 쪽으로
   - **팀 전원 JDK 버전 통일**: sealed / switch 패턴 매칭은 JDK 21+

```java
sealed interface ClientMsg permits Move, UseItem, Ready, Ping {}
record Move(int dx, int dy) implements ClientMsg {}
record UseItem(String item, int targetId) implements ClientMsg {}
// ...

switch (msg) {
    case Move m    -> ...
    case UseItem u -> ...
    // case 하나라도 빠지면 컴파일 에러
}
```

### 초안에 빠져 있던 것

- **단계(Phase) 상태머신**: `LOBBY → ITEM → INTRO → MINIGAME → RESULT → (반복) → FINAL`
- **미니게임 공통 인터페이스**: 시작 / 입력 처리 / tick / 끝났나? / 등수 반환
- **클라이언트 렌더 루프**: `javax.swing.Timer`로 최신 상태를 계속 다시 그리기
- `socket.setTcpNoDelay(true)` (Nagle 알고리즘 때문에 작은 메시지가 지연되는 것 방지)
- **heartbeat**: 몇 초마다 PING, 응답 없으면 나간 것으로 처리

## 2. 수정 구조 기준안

```
[클라이언트]
  키 입력 ──> 송신 큐 ──> 송신 스레드 ──────────────> TCP
  수신 스레드 ──> invokeLater ──> 최신 상태 저장
  Swing Timer(60fps) ──> repaint (최신 상태 그리기)

[서버]
  Accept 스레드 ──> 접속마다 Session(playerId, 송신 큐) 생성
  수신 스레드 xN ──> 파싱 ──> 공용 입력 큐
                                  │
  게임 루프 스레드 x1 (20~30Hz) <──┘
    1. 입력 큐 비우기
    2. 현재 단계 처리 (LOBBY / ITEM / INTRO / MINIGAME / RESULT / FINAL)
    3. MINIGAME이면 현재미니게임.tick()
    4. 상태 broadcast ──> 각 Session 송신 큐
  송신 스레드 xN <── 각자 송신 큐 (LinkedBlockingQueue)
```

스레드 역할이 **받기 / 게임 진행 / 보내기**로 나뉘고, 게임 로직은 루프 스레드 하나에서만 돈다.
수업 12장 구조(Accept 스레드 + 클라이언트별 스레드)에 게임 루프 스레드 하나를 더 얹은 형태.

## 3. 설계 원칙 메모

### N명 구조

- 플레이어는 `player1`, `player2` 변수가 아니라 **목록 + playerId(0~3)** 로 관리
- 모든 메시지에 playerId 포함, 상태 변경은 broadcast가 기본
- 로비에서 최소 2명 ~ 최대 4명, 전원 준비 또는 방장 시작
- 보상표는 **인원수만큼 잘라 쓰기** (예: 6 / 5 / 4 / 4)
- 미니게임은 처음엔 **개인전만** (서바이벌, 점수 경쟁, 레이스). 맵은 4인 스폰 기준으로 만들고 인원수만큼 사용
- 아이템은 "상대에게"가 아니라 **대상 선택**으로 (2인이면 자동 선택)

### 터널링 / 지연 대비

- 판정은 **무조건 서버**. 클라이언트는 입력만 보냄
- 미니게임은 **지연에 강한 장르부터**: 영역 먹기, 아이템 줍기, 장애물 피하기, 반응속도/퀴즈
- 총싸움, 근접 격투처럼 0.1초 차이로 판정이 갈리는 건 나중으로
- 서버 PC 주인이 localhost로 같이 하면 핑 0이라 약간 유리함 (친구끼리면 무시해도 되는 수준)
- 중간에 나가면: 미니게임 꼴찌 처리, 목록에서 제외. 재접속은 2차 목표

### 저주류 아이템을 위한 준비

- 모든 미니게임이 **공통 플레이어 상태(속도, 시야, 크기 등)** 를 따르게 해야 저주가 어디서든 먹힘
- 미니게임 만들기 전에 정해둘 것
